# 基础支撑管理 · 业务原型 v0.1

> **统一入口**：`../prototype-all/index.html` —— 两个模块共用一个可折叠侧边栏（本页面仍可单独打开）。
> 对应文档：`PRD-基础支撑管理-v0.9.docx`（PRD-BS-001）
> 用途：把 PRD 里的文字变成可以点的界面，供业务、开发、测试在**同一个东西**上讨论。
> 声明：纯前端演示，无后端、无真实数据；所有机构名、人名、IP 均为虚构。

## 1. 怎么打开

直接双击 `index.html`，用 Edge / Chrome 打开即可，**不需要安装任何东西、不需要起服务**。

- 建议窗口宽度 ≥ 1366（原型按 1440 设计）。
- 刷新不丢数据（存在浏览器 localStorage）；想恢复初始状态，点右上角「重置演示数据」。
- 按 `Esc` 关闭弹窗 / 抽屉。

目录结构：

```
prototype/
├─ index.html      外壳（侧边导航 + 顶栏 + 内容区）
├─ styles.css      视觉样式（企业后台风格）
├─ data.js         演示数据（应用、会话、参数、消息、接口、审计、规则）
├─ app.js          页面渲染 + 交互逻辑 + 规则校验
└─ README.md       本文件
```

## 2. 为什么先做它，以及它和数据可视化是什么关系

这两个模块**不是一体的**，只是可以共用一个外壳：

| | 基础支撑管理（本次） | 数据可视化系统（下一期） |
|---|---|---|
| 本质 | 能力底座的管理后台 | 数据的消费端 |
| 用户 | 集成方、平台管理员、审计员 | 决策者、业务分析师 |
| 交互 | 表单、审批、监控、留痕 | 拖拽、下钻、联动、大屏 |
| 验收 | 接口调通、权限拦住、指标达标 | 口径一致、时效达标、图表可用 |

先把基础支撑做出来，是因为它的**能力目录（C-01～C-10）**是可视化、质量追溯、生产管理等所有系统的输入。可视化会复用这套外壳和组件，但页面与业务逻辑完全独立。

侧边栏最后一项「数据可视化原型」是一个跳转入口，点进去打开第二个模块：`../prototype-viz/index.html`（13 个页面，已独立完成）。

## 4. 五条演示路径（建议按顺序走）

### ① 接入一个新系统（应用接入）

1. 点「＋ 新建接入申请」，什么都不填直接提交 → 被拦：**应用名称必填**（BR-BS-11）。
2. 填名称/负责人/用途，勾一项能力，回调填 `http://...` → 被拦：**必须 HTTPS**（BR-BS-08）。
3. 改成 `https://energy.corp.local/cb` → 提交成功，状态变「待审核」。
4. 在列表里点该行「审核」→「通过并发放凭证」→ 弹出应用密钥（只显示一次）。
5. 返回列表，应用变「运行中」，右上角待审核红点消失。

> 看的是什么：接入不是“填个表”，而是**申请 → 审核 → 发凭证 → 观察期**四步，每一步都有规则。

### ② 处理一条账号冲突（账号来源）

1. 点任一身份源的「立即同步」，看新增/变更/停用数字变化。
2. 在下方冲突表点「裁定」→ 不填说明直接确认 → 被拦：**裁定说明必填**（BR-BS-07）。
3. 填说明（如“以 HR 为准，AD 为历史遗留工号”）→ 确认，冲突消失。

> 看的是什么：系统**故意不自动合并**。工号重复时自动选边，会把历史单据挂到错误的人身上。

### ③ 改一个设置并回滚（系统设置）

1. 找到 `api.rate.limit`（敏感级），点「修改」。
2. 不填原因直接提交 → 被拦：**变更原因必填**（BR-BS-20）。
3. 填原因，把值改成 `300`，提交 → 先出现「灰度生效中」，1.2 秒后「已生效」。
4. 点该行「回滚」→ 确认 → 值恢复 `200`，审计里多两条记录。

> 看的是什么：**敏感度决定审批强度**（公开/内部/敏感/安全），以及“生效”和“回滚”都必须留痕。

### ④ 发一条会被拦截的消息（消息通知）

1. 选「系统维护通知」（待审核模板）→ 发送 → 被拦：**模板未审核**（BR-BS-29）。
2. 换回「质量异常预警」，打开「模拟 23:00」→ 发送 → 被拦：**免打扰时段**（BR-BS-31）。
3. 紧急度改「紧急」→ 发送 → 放行，但提示“已留痕”（BR-BS-31）。
4. 再打开「模拟短信通道故障」→ 发送 → **自动降级到企业微信**，并记录降级事件（BR-BS-34）。
5. 看下方「到达率」与「发送记录」，每次发送都会更新。

> 看的是什么：同一条消息要过**模板 → 接收人 → 频控 → 免打扰 → 通道**五道关。

### ⑤ 追一次数据导出（操作记录）

1. 在搜索框输入 `李娜`，或把操作类型切到「导出报表」。
2. 点 `LOG-3011` 的「详情」→ 看到六要素与脱敏后的手机号。
3. 点「申请查看原值」→ 不填理由提交 → 被拦；填理由后提交 → 进入待审批。
4. 回列表点「导出审计报告」→ 看到水印与二次审批说明。

> 看的是什么：审计不是“记个日志”，而是**六要素齐全 + 脱敏 + 申请原值要审批 + 导出带水印**。

## 5. 原型里的三个约定

1. **所有操作都会写入审计**。这是刻意的——基础支撑的核心价值就是留痕。你做的每一步，去「审计日志」都能找到（记录号以 `LIVE-` 开头）。
2. **规则编号可追**。页面上的 `BR-BS-xx` 标签对应 PRD 第 6 章，在「业务规则清单」里能逐条确认。
3. **数据是本地的**。刷新不丢，换浏览器/清缓存会重置；「重置演示数据」随时恢复。

---

## 6. 原型边界（没做的部分）

- 不是最终视觉稿：配色、间距、组件会按前端组件库（Vben）重做。
- 没有后端：所有校验写在前端，真实系统由服务端二次校验。
- 没有真实文件/短信/SSO：文件上传只读文件名与大小；消息为模拟发送。
- 未做：多租户、国际化、区块链存证页面、移动端适配（PRD 中为 P1/P2）。
- 图表为 CSS 示意，未接图表库。

- 参数校验 → 生效 → 回滚；
- 身份同步、冲突裁定；
- 会话强制下线；
- 消息的模板拦截、免打扰、紧急放行、通道降级；
- 文件格式拦截与上传成功；
- 接口限流上限、映射试跑；
- 审计脱敏与申请原值；
- 规则勾选、问题结论保存；
- 刷新后状态保持。

结果：**52 passed / 0 failed**。
